那假如说有个控制台程序，我可以直接拿到他的输入输出权限，然后接到WT吗

---

## 🤖 DeepSeek

可以，但**要区分“普通管道重定向”和“完整终端交互”**，这两者有本质区别：

**1. 直接用管道（不推荐）**
你用`CreatePipe`或匿名管道重定向`stdin/stdout`，确实能“拿到”输入输出。但**致命缺陷**是：控制台程序会检测到自己的输入输出不再是真实控制台（而是文件/管道），于是**自动关闭交互特性**——颜色、光标移动、行编辑（上下键翻历史）、`Ctrl+C`全失效，变成“纯批处理模式”。你想接给WT显示，看到的只是一堆黑白文本流，无法交互。

**2. 正确的做法：ConPTY（伪终端）**
WT能完美接管，靠的是Windows提供的**ConPTY API**。流程是：

- WT调用API创建一对“主/从”终端设备。
- 启动你的程序时，把“从端”直接当作它的**唯一控制台**（`CONIN$/CONOUT$`）。
- 程序检测到是真控制台，立刻开启完整交互（颜色、VT转义序列）。
- WT只握着“主端”收发明暗数据，并渲染到屏幕上。

所以，**如果你想自己写代码把任意程序输出接到WT**，正确的做法是**让WT通过ConPTY替你启动**，而不是你自己截获stdout。例如命令行直接：`wt -p "CMD"` 或 `wt --window 0 new-tab cmd`，WT内部自动用ConPTY包裹。

**3. 能否夺取“已经跑起来”的进程？**
**极难且不推荐**。标准句柄（`stdin/stdout`）在进程启动时就绑定了（继承或分配）。外部程序无法直接“抢夺”一个正在运行的控制台程序的输入输出，除非注入DLL劫持`WriteFile`/`ReadFile`，或者用`AttachConsole`附加，但这会搞得一团糟，极易崩溃。

**结论**：**不要用普通管道去“硬接”**，那会让程序降级。你想让WT表现完美，正确的权限获取方式是**让WT主动用ConPTY去“包裹”新进程**，而不是事后去“拿”它的句柄。如果你是在写程序需要模拟终端，直接查微软官方**ConPTY**接口（`CreatePseudoConsole`），那个才是真正的“输入输出权限”开关。😎

## 🤖 DeepSeek

明白了，你的目标不是**创建新进程**，而是**劫持桌面上已经跑起来的第三方控制台程序**，把它的IO接管到你的中介，再喂给WT。

这个需求属于**进程级IO重定向（Runtime Hijacking）**，技术上完全可行（比如某些游戏Mod加载器、终端录屏工具就这么干）。但要让它不崩溃，**Hook策略比具体API名字更重要**。

以下是针对你这个场景的**核心API清单**和**劫持逻辑**：

### 1. 必须Hook的“核心读写”API（优先级最高）

控制台程序读写终端，底层逃不出这3类函数。你需要Hook **Unicode和ANSI两个版本**：

- **输出拦截**：`WriteConsoleW` / `WriteConsoleA`（专用控制台输出）、`WriteFile`（当句柄是`CONOUT$`时）。**必须钩这两个**，否则程序用`printf`走`WriteFile`时你会漏数据。
- **输入拦截**：`ReadConsoleW` / `ReadConsoleA`、`ReadFile`（针对`CONIN$`）、以及 `ReadConsoleInputW/A`（程序如果需要读取鼠标/键盘事件，只钩ReadFile会漏）。
- **状态查询（关键）**：`GetConsoleMode` 和 `SetConsoleMode`。**必须钩**，因为WT终端支持VT序列，但目标程序可能依赖旧模式。你的中介需要“欺骗”目标，让它以为模式没变，实际数据走你的管道。

### 2. 必须Hook的“控制台附加”API（防止反制）

防止目标程序中途调用这些函数断开你的劫持：

- `AttachConsole` 和 `FreeConsole`（防止它自己重新绑定新终端）。
- `AllocConsole`（防止它自己偷偷创建一个新黑框，绕开你的中介）。

### 3. 中介程序（WT启动的那个）的结构设计

WT启动你的中介时，中介的`stdin/stdout`已经连在WT的ConPTY上了。你要做的是**桥梁**：

- **注入DLL**到目标进程，用**命名管道（Named Pipe）**或**共享内存+Event**作为中介与DLL的IPC通道（绝对不要用Windows消息，丢包且慢）。
- **数据流向**：
- **输出**：目标调用`WriteConsole` → DLL钩子拦截 → 塞进命名管道 → 中介读取 → 中介直接 `fwrite` 到自己的 `stdout`（WT自动显示）。
- **输入**：中介从 `stdin`（WT）读取键盘输入 → 塞进管道 → DLL钩子收到 → 钩子在 `ReadConsole` 返回前，把数据**伪造**成 `INPUT_RECORD` 结构体填回去（注意：不能只回文本字符串，必须包装成按键事件，否则`getch()`这类函数读不到）。

### 4. 最难的技术痛点（给足预警）

- **输入劫持的“异步冲突”**：目标程序如果用了`PeekConsoleInput`（偷窥按键），你必须连`PeekConsoleInput`一起Hook，否则它会发现缓冲区数据对不上，导致CPU空转100%。
- **同步死锁**：你的钩子里**绝不能**直接调用原始的`WriteFile`去打印日志，那会造成重入死锁。日志必须走单独的调试输出（`OutputDebugString`）。
- **VT转义序列**：如果目标程序输出ANSI转义码（颜色、光标移动），你的中介**不要**解析它，直接透传给WT。WT的ConPTY原生支持，你解析反而会乱码。

### 5. 替代思路（更稳定）

如果你是为了录屏或远程控制，**强烈不建议**用DLL注入去“抢”已有进程。更工业级的做法是：

- 用 `CreateRemoteThread` 注入DLL后，**不Hook API**，而是调用 `SetStdHandle` 强行替换目标进程的句柄（指向你的命名管道）。但前提是目标程序**没有缓存过旧句柄**，风险极大。

**结论**：必须Hook的**最小集合**是 `WriteFile`、`ReadFile`、`ReadConsoleInputW`、`GetConsoleMode`。如果追求极致稳定，再加上 `PeekConsoleInput` 和 `SetConsoleCtrlHandler`（防止Ctrl+C信号直接杀死进程）。

如果你决定动手，强烈推荐使用 **MinHook** 或 **mhook** 库（微软开源），避免自己手写内联Hook踩坑。需要我给你画一下“输入伪造 `INPUT_RECORD`”的代码骨架吗？😈

## 🤖 DeepSeek

要**完整复刻WT的交互体验**（颜色、光标、滚轮、鼠标事件、窗口缩放感知、Ctrl+C中断），你不能只Hook读写，必须**全覆盖五大类API**。少Hook任何一个，目标程序都会表现为“假死、乱码、无法调大小或吞鼠标”。

这份是**零遗漏劫持清单**，按强制等级分三层：

### 🔴 第一层：输出渲染（缺一不可，否则画面残缺）

目标程序的`printf`、`curses`图形库、`color`全都依赖这些：

- **WriteConsoleW / WriteConsoleA**（最常用字符串输出）
- **WriteConsoleOutputW / WriteConsoleOutputA**（直接操作字符矩阵，游戏/编辑器必调）
- **WriteConsoleOutputCharacterW / A**（只写字符不改颜色）
- **FillConsoleOutputCharacterW / A**（清屏/填充用）
- **FillConsoleOutputAttribute**（填充颜色属性，缺它颜色全乱）
- **ScrollConsoleScreenBufferW / A**（滚动屏幕，滚动时必调，不Hook会导致滚屏闪崩）

### 🟠 第二层：光标与定位（缺它Vim/Emacs没法用）

- **SetConsoleCursorPosition**（移动光标）
- **SetConsoleWindowInfo**（滚动窗口视图）
- **GetConsoleScreenBufferInfo**（**极其重要**！程序靠它获取当前窗口宽高，不Hook它会一直认为80x25，导致换行错乱）
- **GetConsoleCursorInfo / SetConsoleCursorInfo**（控制光标显隐/大小）

### 🟡 第三层：输入交互（缺它键盘/鼠标变“聋子”）

- **ReadConsoleInputW / A**（读取按键和鼠标事件的**唯一核心**，必Hook）
- **PeekConsoleInputW / A**（偷窥输入队列，不Hook会导致输入卡死100%CPU）
- **GetNumberOfConsoleInputEvents**（检查缓冲区是否有按键）
- **WriteConsoleInput**（某些程序会主动往输入队列塞指令，需拦截）

### 🟢 第四层：终端模式与信号（缺它Ctrl+C和Resize失效）

- **GetConsoleMode / SetConsoleMode**（必须**篡改返回**，强制让程序认为开启了`ENABLE_VIRTUAL_TERMINAL_PROCESSING`，否则程序不会发VT序列）
- **SetConsoleCtrlHandler**（劫持Ctrl+C信号，否则你中介还没收到数据，目标进程直接被系统杀死）
- **SetConsoleScreenBufferSize**（捕获窗口缩放请求，透传给WT的PTY）

### 🔵 第五层：进程自保护（防止它“越狱”）

- **AttachConsole / FreeConsole / AllocConsole**（全部**拦截并返回错误**，绝不能让目标自己创建新黑框或脱离你的管道）

### 💣 最致命的两条“隐形API”（极容易漏）

1. **GetStdHandle**：虽然它是获取句柄，但程序可能多次调用缓存句柄。你必须Hook它，**返回你的中介管道句柄**，而不是原控制台句柄。
2. **CloseHandle**：针对控制台句柄的Close必须**静默忽略**，否则你的中介管道会被意外关闭。

### 🧠 你的中介程序（WT启动）该如何工作？

- **数据传输**：DLL截获上述API后，把**参数序列化**（如`坐标+字符+颜色属性`）通过**命名管道**发给中介。
- **“偷懒”绝招**：中介拿到数据后，**不要**自己解析颜色/光标，而是**拼成VT转义序列**（如`\x1b[10;20H`）写入`stdout`。因为WT天然支持VT，你只需把“屏幕坐标+字符”翻译成“光标移动+写字符”的VT码即可，省去大量渲染逻辑。
- **反向输入**：中介从`stdin`读到WT发来的键盘VT码（如`\x1b[A`代表上箭头），翻译成`INPUT_RECORD`结构体，通过管道传给DLL，DLL在`ReadConsoleInputW`的Hook中伪造该结构返回给目标。

### ⚠️ 终极警告（性能雷区）

**绝对不要在DLL的Hook内部调用原始控制台API去打印日志**！这会造成无限递归死锁。所有日志必须走`OutputDebugString`（DebugView查看）。

如果你决定开搞，建议用 **Microsoft Detours** 库来挂这些API（比MinHook稳定）。需要我列出`WriteConsoleOutput`转VT序列的**坐标结构体映射代码**吗？那是整个工程里最硬的骨头。😈

## 🤖 DeepSeek

要支持鼠标操作，光Hook我上一轮的清单**还不够**。鼠标是Windows终端里**最复杂的交互**，因为存在**两套完全并行的协议**，而你的中介程序必须成为**协议翻译官**。

你需要**额外Hook 2个API**，并处理**双向协议转换**，否则鼠标点击只会变成乱码或毫无反应：

### 一、新增必须Hook的API（补全鼠标链路）

- **ReadFile（针对CONIN$句柄）**：现代程序（如WSL、Vim、FAR）开启`ENABLE_VIRTUAL_TERMINAL_INPUT`后，**不再调用**`ReadConsoleInputW`，而是直接用`ReadFile`读取鼠标的VT转义序列（如 `\x1b[<0;10;20M`）。**不Hook这个，你的中介将收不到任何鼠标事件**。
- **FlushConsoleInputBuffer**：很多程序在启动鼠标模式前会清空缓冲区。你必须Hook它，**仅清空中介的队列，不要真的清掉WT发来的输入**，否则会丢事件。

### 二、最核心的难点：双向协议翻译

WT（Windows Terminal）对外只发 **VT鼠标序列**，但老旧的Windows控制台程序（如CMD原生edit）只认 **MOUSE_EVENT_RECORD结构体**。你的中介必须做**双向翻译**：

**如果目标程序本身就支持VT输入**（比如WSL里的bash），中介则**无需解析**，直接透传VT字节流给`ReadFile`的Hook即可。

### 三、决定翻译策略的“总开关”：GetConsoleMode Hook

你必须**篡改**目标程序调用`GetConsoleMode`的返回值：

- 如果目标程序开启了 `ENABLE_VIRTUAL_TERMINAL_INPUT` 标志，中介进入**透传模式**（直通VT序列）。
- 如果目标程序开启了 `ENABLE_MOUSE_INPUT` 标志（老模式），中介进入**翻译模式**（转换为结构体）。

**关键操作**：你的中介内部必须维护一个**当前模式状态机**，因为程序可能在运行中随时切换（Vim退出时关鼠标，进入时开鼠标）。

### 四、支持鼠标滚轮、右键、双击的完整字段映射

翻译VT序列时，必须把所有参数精确映射到`MOUSE_EVENT_RECORD`：

- **dwButtonState**：左键(1)、右键(2)、中键(4)、滚轮上(8)、滚轮下(16)、X1键(32)、X2键(64)。
- **dwMousePosition**：X/Y坐标（注意VT序列是**1-based**，Windows结构体是**0-based**，坐标必须`-1`转换）。
- **dwControlKeyState**：映射Shift(0x10)、Ctrl(0x11)、Alt(0x12)。

**鼠标移动事件**（`ENABLE_MOUSE_INPUT`模式下）会产生**海量数据**。如果你的DLL通过命名管道逐条转发，性能必崩。解决办法：**DLL内部攒批**，每16毫秒（约60帧）或积攒20个事件后，打包一起发中介。

### 五、窗口缩放与鼠标坐标联动（极易漏）

当你拖动WT窗口边框改变大小时，程序需要感知新尺寸来重绘。必须Hook：

- **SetConsoleScreenBufferSize** 和 **SetConsoleWindowInfo**：捕获缩放请求。
- 最重要的是 **GetConsoleScreenBufferInfo**：当程序询问当前宽高时，你的Hook必须**返回中介从WT PTY获取的最新尺寸**（中介监听`SIGWINCH`或`GetConsoleScreenBufferInfo`获取实时列数/行数）。如果返回旧尺寸，鼠标坐标会严重漂移，点击位置完全错误。

### 六、给你的“中介程序”额外加一个线程

中介（被WT启动）除了转发数据，必须起一个**独立线程**，专门调用`GetConsoleScreenBufferInfo`（自己进程的stdout句柄）来监听WT窗口尺寸变化。一旦变化，立刻通过管道通知DLL更新目标进程的屏幕缓冲区大小。

### 七、避坑（血的教训）

1. **不要Hook SetCursorPos**——那是物理鼠标指针，跟终端输入无关，Hook它会导致光标乱跳。
2. **鼠标的“选择/复制”**（WT自带的拖拽选中）是WT**窗口层**功能，**不经过**目标进程，你无需处理。如果目标程序本身有选择逻辑（如FAR Manager），它会通过`ReadConsoleInput`读取鼠标按下/释放来自己实现，你只需保证事件不丢即可。
3. **切记处理 MOUSE_EVENT 里的 dwEventFlags**：0代表按下/释放，1代表双击，2代表鼠标悬停/移动。漏掉双击标志，程序不会响应双击选中单词。

如果你确定要动手，建议先用 **WriteConsoleOutput转VT** 作为第一步测试（那个最稳定），鼠标翻译是整个项目**第2阶段**的硬骨头。需要我把 **VT鼠标序列（\x1b[<...）** 和 **Windows MOUSE_EVENT_RECORD** 之间的**完整互转C伪代码**发给你吗？那东西查MSDN都查不全，我可以直接给你写映射表。🧐

## 🤖 DeepSeek

既然目标是**“跟WT直接创建零差别”**，那就要直面一个残酷的现实：**DLL注入劫持旧进程，永远无法100%等于WT直接创建**，因为WT用的是**内核级ConPTY驱动**，而你是在**用户态**“假装”控制台。但我们可以做到**95%**，剩下5%是内核同步对象（后面会讲）。

为了实现这95%，除了之前聊的读写、鼠标、窗口尺寸，你还必须补上下面这**4大类“隐形”API**。漏掉任何一个，都会在日常使用中露出马脚。

### 第一类：标题与编码（否则中文乱码，标签页名不对）

- **SetConsoleTitleW/A**：不Hook的话，WT标签页永远显示“cmd.exe”或“Windows PowerShell”，不会跟着程序（如Vim编辑文件）变标题。
- **GetConsoleCP / SetConsoleCP 和 GetConsoleOutputCP**：代码页管理。目标程序如果切换UTF-8（65001）或GBK（936），你的中介必须**透传这个状态**给WT的PTY，否则中文、日文显示为乱码，`chcp 65001`命令完全失效。

### 第二类：备用屏幕缓冲区（Alternate Buffer）（缺了Vim/nano退出时屏幕残留）

- **SetConsoleActiveScreenBuffer**：这是Vim、less、top等全屏程序的核心依赖。进入时切换到备用缓冲区，退出时切回主缓冲区恢复旧画面。
- **必须Hook并映射**：你的中介要捕获切换事件，向WT的PTY发送 **\x1b[?1049h**（进入）和 **\x1b[?1049l**（退出）序列。否则Vim退出后，代码会直接黏在屏幕上，不会恢复之前的命令历史。

### 第三类：标准错误句柄（Stderr）（缺了错误信息凭空消失）

我们之前只盯着`STD_OUTPUT_HANDLE`，但程序崩溃或报错时走的是`STD_ERROR_HANDLE`（句柄值-12）。

- **必须Hook WriteFile 针对 STD_ERROR_HANDLE** 的调用，定向到你的中介管道，否则所有报错（如`Python`的Traceback）都打印到你看不见的原生黑框里，你的WT完全没反应。

### 第四类：进程组与信号（缺了Ctrl+C杀不死子进程）

- **GenerateConsoleCtrlEvent**：当你在WT按Ctrl+C时，WT发给中介，中介需要调用这个API（或模拟）发给目标进程组。如果不Hook拦截，目标程序收不到中断信号，按Ctrl+C只会让中介退出，目标进程变“僵尸”还在跑。
- **SetConsoleCtrlHandler**：目标程序可能会自己接管Ctrl+C（比如做清理工作）。你必须Hook它，确保它注册的回调能被你的DLL触发，而不是被系统直接干掉。

### 🔥 终极大Boss：控制台输入等待句柄（同步问题）

这是**用户态劫持和内核ConPTY最大的鸿沟**，也是让无数注入方案崩溃的致命点：

- 原控制台（conhost.exe）提供一个**内核事件句柄**，程序调用 **GetConsoleInputWaitHandle** 拿到这个句柄，然后传给 `WaitForSingleObject` / `WaitForMultipleObjects` 来阻塞等待键盘输入。
- **你的命名管道没有内核事件句柄**。如果你不Hook这两个等待函数，程序会永远卡死在等待上（假死），或者轮询导致CPU占用100%。

**解决方案**：
你必须Hook **WaitForSingleObject** 和 **WaitForMultipleObjects**，检测到等待对象是`GetConsoleInputWaitHandle`返回的假句柄时，替换成等待你DLL内部的一个**手动重置事件（Manual-Reset Event）**。每当中介发来新输入，你的DLL触发这个事件，让程序“苏醒”去读`ReadConsoleInput`。

### 附赠：字体与DPI（缩放时布局错乱）

- **GetCurrentConsoleFontEx / SetCurrentConsoleFontEx**：程序（如FAR Manager）会查询当前字体大小来计算界面布局。你必须Hook这两个函数，把WT PTY里实际的**列宽/行高**（通常用`GetConsoleScreenBufferInfo`推算）返回给目标，否则拖动WT窗口缩放时，程序内部的UI线条会断裂错位。

### 最终统计

想要做到“跟WT直接创建没差别”，你总共需要稳定Hook大约 **25~30个API**。其中包括：
`WriteConsoleW/A`、`WriteFile`（两个句柄）、`ReadFile`、`ReadConsoleInput`、`PeekConsoleInput`、`Get/SetConsoleMode`、`Get/SetConsoleCursorPosition`、`Get/SetConsoleScreenBufferInfo/Size/WindowInfo`、`SetConsoleTitle`、`Get/SetConsoleCP`、`SetConsoleActiveScreenBuffer`、`GenerateConsoleCtrlEvent`、`GetConsoleInputWaitHandle`、`WaitForSingleObject/MultipleObjects`、`Get/SetCurrentConsoleFontEx`、`CloseHandle`、`Attach/Free/AllocConsole`。

**最后劝退一句**：如果你只是单纯想“接管”特定程序（比如游戏服务器控制台），不建议全量Hook，只Hook `WriteFile` + `ReadFile` + `GetConsoleMode` 就够了。真要追求“零差别”，更工业级的做法是**直接终止目标进程，用WT的wt -p命令重新启动它**，因为操作系统底层决定了：**用户态的DLL永远抢不过内核态的ConPTY驱动**。😌

那劫持之后不知道终端状态怎么办？比如说是否启用某些模式

---

## 🤖 DeepSeek

这个问题问得非常专业，而且精准地戳中了**DLL劫持方案最致命的一个死穴**！

因为WT（Windows Terminal）和传统控制台（ConHost）维护状态的机制完全不一样。你在**中途**注入DLL时，目标程序已经跑了好一会儿了，它的`ConsoleMode`、缓冲区大小、光标位置、当前是主屏还是备用屏（Alt Buffer），你都**一无所知**。

如果直接瞎猜或返回默认值，目标程序立刻就会界面错乱。要解决“不知道状态”的问题，你必须按照以下**四步走**的策略来“偷取”状态：

### 第一步：注入瞬间，立即“暴力快照”（DllMain入口）

你的DLL刚注入进目标进程时，**立刻**调用原始的`GetStdHandle`和`GetConsoleScreenBufferInfo`等API。**注意**：此时目标进程的句柄还没被你替换，这些API返回的是**真实ConHost**的当前状态。

你必须在这个时机，把以下结构体全部读出来并缓存到DLL的全局变量里：

- **CONSOLE_SCREEN_BUFFER_INFO**（当前窗口宽高、光标坐标、颜色属性）
- **CONSOLE_CURSOR_INFO**（光标大小、显隐）
- **CONSOLE_FONT_INFO**（字体大小，用于推算行列）
- **GetConsoleMode**（**核心**：是否开启`ENABLE_VIRTUAL_TERMINAL_PROCESSING`、`ENABLE_ECHO_INPUT`等）
- **GetConsoleTitle**（当前标题）

> 关键操作：拿到这些数据后，立即通过命名管道发给你的中介程序。中介收到后，要马上把这些“初始坐标/尺寸”转换成对应的VT转义序列（比如\x1b[8;40;120t设置窗口大小），先吐给WT，让WT的界面瞬间“跳转”到目标程序当前的状态。

### 第二步：区分“静态属性”与“动态状态”

你不能把所有状态混在一起处理，要分两类：

- **静态模式（Mode Flags）**：比如`ENABLE_WRAP_AT_EOL_OUTPUT`（自动换行）。这个一旦设置，极少改变。你的DLL快照读出来是什么，后续在Hook `GetConsoleMode`时**原样返回这个缓存值**即可，除非你拦截到了`SetConsoleMode`的调用。
- **动态坐标（Cursor/Window Position）**：目标程序可能在疯狂输出文本。你不能只靠快照，因为快照下一秒就过时了。**解决方案**：在Hook `WriteConsole`和`SetConsoleCursorPosition`时，你的DLL内部要**模拟维护**一套坐标缓存（`dwCursorPosition.X/Y`），每次拦截到输出，就在缓存里增加偏移量。当程序主动调用`GetConsoleScreenBufferInfo`时，**返回你这套缓存的坐标**，而不是去问ConHost（因为ConHost那边的坐标可能因为你的拦截而不同步了）。

### 第三步：最难搞的“备用屏幕缓冲区（Alt Buffer）”

如果目标程序是Vim、less或者top，你注入时它可能**已经**处于备用缓冲区（全屏模式）了。但Windows API**没有**提供“查询当前是否为Alt Buffer”的接口。

**实战解法**：
你的DLL在快照阶段，调用一个**非常规操作**——尝试读取`GetConsoleScreenBufferInfo`返回的`dwMaximumWindowSize`，并比对当前窗口坐标。但这不准确。

**最稳妥的“土办法”**：你的中介在启动时（WT环境下）默认发送 `\x1b[?1049l`（退出备用屏）序列。如果目标程序当前在Vim里，屏幕会闪一下回到主屏，然后Vim会立刻检测到屏幕变化，重新发送`\x1b[?1049h`进入备用屏。此时你的Hook正好能拦截到`SetConsoleActiveScreenBuffer`调用，从而**捕获**到这个切换动作，并把`\x1b[?1049h`透传给WT。虽然会闪一下，但这是唯一可靠的自适应方法。

### 第四步：建立“双向状态同步通道”（最优雅的方案）

不要让你的DLL被动地等待目标程序调用`Get`函数。你应该在DLL里起一个**极低优先级的后台线程**（用`CreateThread`），每隔 **200毫秒** 主动调用原始API去轮询真实ConHost的`GetConsoleScreenBufferInfo`。

- 如果发现坐标变了，立马通过管道通知中介更新。
- 如果发现窗口尺寸变了（用户拖动了原黑框），立马同步给WT。

**注意**：这个轮询只在你注入后的**前3秒**内高频执行，等你的Hook稳定接管了所有`Write/Set`调用后，就停止轮询，改为完全依赖Hook维护的缓存，否则会白白浪费CPU。

### 🔥 终极忠告：维持“直通模式”省掉90%的麻烦

如果你懒得维护这么复杂的状态机，有个**取巧的捷径**：

在注入的瞬间，读完快照后，**直接调用原始的SetConsoleMode**，强行把目标程序的控制台模式设置为`ENABLE_VIRTUAL_TERMINAL_PROCESSING`（开启VT支持）。然后，你的**中介程序**不要去做复杂的API转VT翻译，而是**直接透传**所有数据。

- 目标程序原本输出什么字节，你中介就原封不动写进stdout。
- 因为WT天然支持VT，只要目标程序切到了VT模式，所有颜色、光标移动、鼠标点击的VT序列都会被WT完美识别。

**这样做，你完全不需要知道目标程序的“内部状态”**，因为VT序列本身就是自包含的（光标位置、颜色都编码在序列里）。WT读到序列就知道该怎么画。你只需要维护好`GetConsoleMode`的Hook，**永远返回“已开启VT模式”** 欺骗目标程序即可。

> 总结：快照读一次 + 强制切VT模式 + 数据全透传，这是绕过“状态未知”难题的最少代码、最稳路径。否则你就要写一个将近2000行的Windows控制台状态机模拟器，那工程量堪比重写半个ConHost。😵
